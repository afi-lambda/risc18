## 1. The recipe

Make the decisions in this order, but treat the first routed full-system build as feedback on the architecture, not as a final implementation detail.

1. **Choose the workload and memory semantics, then the ISA and width.** For a word-oriented workload, keep the 18-bit Harvard ISA, fixed-width instructions, and cheaply extracted register fields. Decide up front whether byte pointers, large objects, or an existing compiler ABI are requirements. The 39.15 MHz RV32I build shows that a straightforward wider implementation can route poorly; the roughly 70 MHz VexRiscv system shows that 32 bits is not itself a timing barrier. Choosing 32 bits unnecessarily spends storage and datapath resources; choosing 18 bits for byte-heavy software can spend more instructions than it saves in hardware. Compare useful work per second on the same task, not ISA-level MIPS alone.

2. **Budget the pipeline around synchronous memory and the dependency loop.** Keep the present five-stage machine as the baseline. Resolve general conditional branches in X and keep the registered redirect that demonstrably broke the old timing loop. Separately design the *predicted* next-PC path and the *recovery* path. The move from roughly 48 MHz to at least 60 MHz supports breaking the redirect loop, not accepting four lost cycles forever. Earlier resolution can recreate a loop through operand selection, comparison, and PC control; deeper staging can move the bottleneck from fmax to dependency and branch bubbles. The J1 result is evidence that a shallow pipeline can work with a different operand model, not that a three-stage risc18 wins.

3. **Specify the memory service contract before optimizing the datapath.** Start with independent synchronous EBR instruction and data stores so a load or store need not steal an instruction read. Specify request-to-response timing, read/write collision semantics, and which accesses can stall. Allocate EBRs against the intended footprint, including any future cache, not the address width. Two EBRs make the current core small; the PDP-8’s 48 blocks show how quickly a system can become memory-bound in *capacity*. A shared single-access store creates structural stalls; assuming all memory behaves like local EBR hides the costs of a larger system.

4. **Use the distributed-RAM register file, and design forwarding with it.** The area case is already settled for this baseline: 1,813 to 1,183 LUT4s and 605 to 407 FFs. The fmax case is not: the flop build reached 73.89 MHz on one seed. Optimize the path from source identification through hazard selection to the operand register, not just the storage element. A flop file buys flexibility at an area and routing cost; putting a tiny multi-read file in synchronous EBR can force replication or another stage, changing the hazard schedule.

5. **Use fabric carry chains for ordinary adds and hard multipliers for real multiplies.** Keep simple ALU and address adds local. Exploit 18×18 multiplication when it replaces useful work, and budget its result latency and full product width. One multiplier in M11 demonstrates a cheap resource fit, not a MAC throughput win or a free accumulator. Moving simple address generation into a DSP-based structure can add placement and latency constraints; implementing a full multiply in LUTs needlessly consumes fabric unless a specific workload or timing requirement justifies it. The collapsed target-adder experiment is the right warning: saving arithmetic is not the same as shortening the limiting path.

6. **Optimize and sign off the complete placed system.** Compare variants under matched constraints and several paired seeds; inspect the recurring path families and their routing, not the best seed alone. M11’s limiting path is about half routing, and its full-top report is 67.59 MHz versus 73.48 MHz core-only. Those facts make locality, select fanout, and the full-system build more relevant than another small adder rewrite. Finally validate the actual clock, timing constraints, and function on hardware. A core-only fmax is neither a board clock nor an observed retirement rate.

The invariants are workload-first design, explicit latency and port budgets, controlling dependency loops, and measuring delivered throughput. The ECP5-specific choices are 18-bit EBR packing, distributed LUT RAM, the 18×18 multiplier, carry-chain mapping, and routing to fixed hard blocks. The **25K device** makes the finite block count and placement budget particularly important; it does not prescribe five stages.

## 2. What 18 bits actually buys

The strongest win is **memory width at a given depth**: a 1,024-word 18-bit store fits one block, while a 1,024-word 32-bit store needs at least two. That applies independently to instructions and data if both really are 18 bits wide. The next strongest win is a native full-width multiply in one hard multiplier; a general 32×32 multiply does not fit one. You also save bits in register storage, operand muxes, pipeline registers and adders. Narrower adds and buses can help timing, but a dependency path dominated by register-tag comparisons, mux selects and routing does not get 18/32 as long. The table has no controlled width-only experiment.

The costs are real. An 18-bit word does not naturally provide a conventional byte-addressed ABI. Packing two octets with two bits left over is possible, but addressing, extraction, and subword stores still need a policy and possibly extra operations. With two four-bit register specifiers, only ten instruction bits remain for opcode and immediate combined; larger constants, offsets and targets may expand into more instructions. A 16-bit address names 65,536 locations, not necessarily 65,536 bytes; if word-addressed, it names that many words, most of which cannot be backed by on-chip EBR. A custom compiler backend, ABI, debugger and libraries are costs that a mainstream ISA largely avoids. Even a clean CPI comparison can hide a larger dynamic instruction count.

**Bluntly: 18 bits is defensible as a performance target for a compact, word-native machine with a known workload. It is a handicap as a general-purpose software target.** The deciding experiment is equal-output runtime, code footprint and memory traffic against a credible 32-bit implementation, not 73.48 versus 39.15 MHz.

## 3. Next levers, ranked

This is the order I would spend engineering weeks in. Bring-up is first for information value, not because it adds MIPS. The rest assumes the target workload mostly fits in local memory; if it does not, memory moves to the top after bring-up.

1. **(i) Hardware-in-the-loop at 60 MHz.** Verify results, retirement counts and cycle counts against simulation. Direct speed gain: zero. Risk: low, provided instrumentation is checked for timing perturbation. This turns the rest of the ranking into a board optimization rather than a simulation exercise.
2. **(c) Audit redirect-to-retirement timing and remove any avoidable front-end bubble.** Check whether the redirect target can be accepted a cycle sooner with the existing registered redirect, and whether a valid target response is unnecessarily held off or killed. One actual cycle recovered per taken branch takes the example from 56 to 52 cycles, about 8% at equal clock. The main risks are stale EBR responses and accidentally restoring the X-to-fetch combinational path.
3. **(g) Cut the bypass-control cone and raise the verified clock.** Move source identification or dependency classification earlier where the instruction interface permits; evaluate precomputed selects, local control replication, and a more local operand mux. Preserve load-use and forwarding behavior. Even 60 to 67 MHz at unchanged CPI is about 12%, but a reported timing improvement delivers nothing if the PLL stays at 60 MHz. Extra staging that inserts dependency stalls can lose more than it gains.
4. **(a) Predict next PC before moving branch resolution into D.** Backward-taken/forward-not-taken is a *static* rule; a last-outcome bit is a different predictor. Start with the cheap rule if the target can be supplied early enough to save real request cycles. Consider a small tagged target structure if EBR instruction arrival makes that too late. Keep X verification. D resolution is a separate, lower-priority experiment: dependent branches require early operands, and the decode/forward/compare/redirect loop may undo the original timing win.
5. **(b) Try direct distance-one forwarding only against measured dependency bubbles.** If it removes a real stall, measure the gain; if forwarding already sustains one dependent instruction per cycle for that producer class, it buys no CPI. A direct `x_value` path can join an X computation to a D operand mux and register, making two stages share one timing budget. Don't assume that eliminating an operand split shortens the worst path.
6. **(e) Build a memory hierarchy for a footprint that needs one.** First consider banked local stores or a software-managed scratchpad; add a cache when measured locality and backing-memory latency justify it. There is no hit-rate upside over the current stall-free local access on fitting workloads. There can be enormous end-to-end upside when the alternative is slow external access or not running at all. Miss handling, port conflicts and write policy are the risks.
7. **(f) Add MAC only for a demonstrated kernel.** It can improve useful work per second by reducing instructions, even if retired MIPS falls. Ordinary address generation has no demonstrated DSP upside here. Check accumulation width, state or register dependencies, and multiplier latency before setting an expected gain.
8. **(h) Prototype three stages only with a measured break-even target.** It's a redesign of the hazard and memory schedule, not a guaranteed CPI improvement. At 48 MHz versus 60 MHz and baseline CPI 1.615, it must get below CPI 1.292 just to win. Compare routed full tops, including branch-heavy *and* dependency-heavy code.
9. **(d) Defer width.** Two-wide fetch alone doesn't raise the single-issue retirement ceiling; it might help refill or predict ahead, but compare it to a small fetch buffer first. Dual issue means more instruction bandwidth, register ports, dependency checks, bypassing and conflict handling. There's no evidence yet that independent issue opportunities repay all that in this core.

## 4. Arithmetic and the four slots

The arithmetic checks out, with an important distinction between a modeled core rate and a board result. **73.48 / 1.615 = 45.50 MIPS**. At 60 MHz the same CPI implies **37.15 MIPS**. The loop itself has CPI **56 / 35 = 1.600**. If the only change is to remove 16 elapsed cycles, it becomes **40 / 35 = 1.143**, and the throughput ratio is **56 / 40 = 1.40** at equal clock. With a changed clock, multiply that ratio by the new-to-old frequency ratio.

The conditional is important: **four invalidated fetch slots are not necessarily four incremental elapsed cycles**. Confirm the 16-cycle attribution with a trace or an ideal-next-PC simulation using the same retirement endpoints, with identical memory and non-control hazard behavior. The 1.40× is a ceiling on eliminating those particular costs under those assumptions, not on all possible optimizations.

- **Static backward-taken:** for this backward loop branch, it gets the four taken outcomes right and the exit wrong. With zero cost on correct predictions and a four-cycle exit recovery, the estimate is **44 cycles, 1.27×**, not 40. Even one cycle on each correct transfer makes it **48 cycles, 1.17×**. Measure through a common post-loop retirement so the exit cost isn't cut out of the window.
- **Last-outcome bit:** with a cold not-taken initial state, expect a first-taken miss and an exit miss, or **48 cycles** under the same idealized four-cycle recovery assumptions. Initial state, aliasing, and when the target becomes available matter. A direction bit without a timely target is not a zero-bubble predictor.
- **Earlier resolution or shorter recovery:** if either saves exactly one elapsed cycle on each of the four taken transfers, it gives **52 cycles, 1.077×**. For D resolution, a clock loss greater than about 7.1% erases that gain. Count stalls for branches consuming recent results; resolve-stage labels alone don't predict the savings.

**Four is not a minimum implied by five stages and synchronous EBR.** EBR constrains the interval from a sampled target address to a usable instruction, not how many cycles your PC, redirect and valid logic take to get there. Trace the X decision, redirect register, first target address sampled by EBR, response validity, D acceptance and target retirement. If a registered redirect is already available but the EBR samples a stale PC for one more edge, or the first valid target response is suppressed by flush logic, a slot may be recoverable without removing the redirect register. If neither happens, there is no evidence for a free slot. A redirect-to-address mux change still needs timing sign-off.

## 5. The cliff you haven't listed

The likely cliff is **the transition from a local-memory CPU to a memory system**. Correct the port premise: DP16KD is true dual-port in supported configurations, including two 18-bit-capable ports; a particular inferred 1R/1W instance is not the primitive's full capability. That does not give arbitrary independent accesses, well-defined results for every same-address collision, or free ports for CPU accesses, refill, debug and DMA all at once. Check the configured mode and collision rules.

At the stated packing, 56 blocks hold **57,344 18-bit words in total**, before any replication, tags, buffering, instruction/data partitioning or wasted depth. A fully backed 64K-word space already exceeds that, even before considering a separate Harvard space. The PDP-8 numbers are evidence of block pressure, not a universal conversion from architectural address space to physical memory. Also distinguish native write enables in a chosen EBR mode from **ISA byte lanes**: the current word interface doesn't acquire byte stores merely because an EBR mode offers subword enables. Emulating packed-byte stores through read-modify-write consumes accesses and raises atomicity issues when there are other agents.

Once the working set spills, backing-memory **latency, bandwidth and access granularity** can dominate. A single-issue blocking core pays exposed miss latency directly in CPI; making its ALU faster may barely change elapsed time. Conversely, if the workload stays local, cache machinery can be pure overhead. Measure extra stall cycles per retired instruction across working-set sizes, not just external bus peak bandwidth. That curve tells you whether you're tuning a CPU or need to design its memory system.

## 6. Honesty check

A tiny benchmark is a good diagnostic and a bad headline. The defensible variants are:

- **Branches and fetch (a, c):** use the tiny loop to validate exact penalties, then report cold and warm behavior on multiple branch patterns, including exits, forward branches, dependent branches and target conflicts. Don't count a warmed, repeatedly taken branch as general prediction accuracy.
- **Bypass, clock and pipeline (b, g, h):** use a dependency microtest to prove the mechanism, then include loads, mixed producer-consumer distances and independent streams. Publish full-top clock and same-binary hardware throughput, not a best-seed core clock multiplied by unrelated simulated CPI.
- **Width (d):** don't extrapolate from hand-paired independent instructions. Report sustained retirement and useful work with ordinary scheduling, branches, memory conflicts and realistic dependency density.
- **Memory (e):** label a 16-word image in a 1,024-word store as an ideal-residency test. Publish a footprint sweep and include cold start and backing-memory traffic when claiming system throughput.
- **MAC (f):** use identical numerical results and precision, and report kernel and end-to-end time. Fewer retired instructions can be the improvement.
- **Bring-up (i):** don't call a successful demo a performance result. Count architectural commits and elapsed cycles over a validated region, and state what setup and completion work is excluded.

A 13-instruction test can settle a hazard question. It cannot establish representative CPI, and cross-ISA MIPS cannot establish which CPU finishes the same job first.

## 7. What to measure first

Measure **hardware cycles per committed instruction at verified 60 MHz, with a mutually exclusive breakdown of lost retirement opportunities**, on one representative workload with checked outputs. Attribute bubbles to control recovery, data hazards, instruction supply and data-memory waits; keep a short redirect trace to validate the attribution against the simulator. If the intended workload cannot fit in the current stores, say so before choosing the test: a local-memory stand-in cannot settle the memory-system ranking.

That measurement tells you which CPI gains are actually available. Compare each removable fraction of elapsed cycles with the plausible clock gain; for example, removing about **11%** of elapsed cycles at 60 MHz matches raising the clock from 60 to 67.59 MHz with CPI unchanged. It also tests whether the four-slot story survives contact with hardware.

I would abandon **the current pipeline shape**, not necessarily the ISA, if the measured workload has large, recurring control or dependence losses that are intrinsic to the stage boundaries, **and** a matched, routed shorter-pipeline prototype clears the throughput break-even with margin on the same work. High branch CPI alone does not meet that test if fetch recovery or prediction can fix it. If waits instead come predominantly from a required working set beyond local EBR, abandon the **local-only memory assumption** first; changing the number of pipeline stages does not solve it.
