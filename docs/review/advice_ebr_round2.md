The quoted 1.9 ns net alone leaves just 1.5 ns for the carry chain, remaining routing, and destination timing in that estimate. Use the full path report for the budget, not a second sum of approximate components. Likewise, the worst split result is 21% above 120 MHz in frequency, or about 1.44 ns of slack against an 8.33 ns period.

   A 5.6 ns clock-to-DO budget is plausible for an unregistered read on a -6 ECP5. I don’t have a verified vendor number for the exact part and mode that would justify replacing it with 3 ns. 2. **Sweep the clock on a functional read test, not a ring oscillator.** Start with the routed split probe. Initialize the EBR with complementary words and alternate the read addresses so the tested outputs have to toggle on every read. Keep the launch addresses comfortably timed—for example, prepare them on the preceding falling edge if that path is verified over the sweep. Capture into the same fabric register as in the probe, and check the captured stream with a sticky error flag. Read the result over UART in a stable clock domain. Make the checker noncritical and run a control that exercises the checker without the EBR path. Keep the measured EBR, capture flop, and data route fixed across frequency points; don’t compare independently placed builds as if frequency were the only variable.

   Near 150 MHz, a 1 MHz sweep step is about **44 ps of period**. That’s nominal step size, not measurement accuracy; use the actual legal PLL settings and bracket the transition with repeated runs. The result is a pass/fail threshold for **clock-to-DO plus routed delay and capture timing**, on this board at the tested voltage and temperature. It does not isolate clock-to-DO to tens of picoseconds. The failure mode is finding the limit of the address launch, PLL/clock network, checker, or write half instead of the read path. I’d isolate the read first, then sweep the actual EBR→add→EBR datapath, which is the experiment that directly informs the architecture decision. A ring or delayed replica adds calibration problems without making that decision easier.

3. **Choose single-cycle if it closes the full-core timing budget and improves useful throughput.** At 120 MHz, a real 6.4 ns path would leave about 1.9 ns for integration and guardband; that would make single-cycle a serious candidate. At 150 MHz it would leave only about 0.27 ns, before any integration penalty. The acceptance criterion is closure of the *integrated* core across representative placements and the required operating envelope, including operand selection, write enables, addresses, bypasses, and control—not just an isolated adder probe. Among the versions that pass, compare workload cycles per instruction and resource cost at the required clock. If both close at 120 MHz and single-cycle removes dependency stalls or bypass logic, take it. If single-cycle only passes on the bench or relies on an unvalidated timing exception, keep the split. The split itself is not yet a robust 150 MHz solution in the reported seeds.

4. **Rank the options by whether they remove the read arc or merely rearrange storage.**

   **First, use distributed RAM for a small, timing-critical register file or table.** It replaces the EBR clock-to-DO path with a fabric address-to-data path and can provide a combinational read without the EBR read-cycle boundary. It costs LUTs and routing, with deeper arrays adding mux levels. Budget replication for independent read addresses where the mapped primitive cannot supply them; replicated banks must all receive writes. For a very small register file, also price flops plus muxes: higher storage cost can buy simpler port and bypass behavior.

   **Second, keep hot operands in fabric registers and leave bulk storage in EBR.** Explicit architectural accumulators or a small operand buffer can remove the EBR read from common operations. This costs flops, selection and update logic, and potentially a miss or refill cycle. It moves the read off the critical path for hits only; it does not accelerate arbitrary EBR accesses.

   **Third, use 36-bit mode only if both 18-bit halves are useful together.** It can deliver two packed values from one wide address, subject to the primitive’s port and write-enable constraints. It doesn’t give two independent read addresses or remove the read stage. Packing can save blocks or accesses; selecting just one half can add a mux, and independent updates may be less convenient.

   **Fourth, interleave across two EBRs for bandwidth, not latency.** Each bank still has a full EBR read arc. Banking costs block resources or utilization, bank steering and often a return mux; same-bank requests can still conflict. It helps if the workload can exploit independent banks or keep their outputs separate. Otherwise the return mux can make the read path worse.

   **Last, narrow the memory and select bytes or subwords only for a packing or interface reason.** Fewer active bits can reduce routing, but a narrower configuration is not evidence of lower clock-to-DO. If an 18-bit operand needs multiple narrow accesses, you pay in ports, blocks, or cycles; if the data is read wide and selected afterward, you pay in mux logic. Neither inherently moves the read boundary.

5. **The trap is paying for the second stage without getting one useful operation per cycle.** A dependent instruction can launch its EBR read before the preceding writeback is visible. If the design treats that as an ordinary memory access, same-address read/write behavior may not give the value the ISA requires. Fixing it with stalls can push dependent code toward one operation every two cycles; fixing it with forwarding can put tag compares, priority muxes, and writeback fanout on paths absent from the probe. A late stall or redirect can also leave a stale read in flight unless its valid bit and destination travel with it. Before committing, close timing on the dependency and writeback paths and measure a back-to-back dependent instruction stream. That test tells you whether the split is a pipeline with useful overlap or just a two-cycle execution unit.
