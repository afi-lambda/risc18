## 1. Rank the fmax levers

**First RTL change: simplify the D-stage dependency checks and bypass selection.** First experiment: a short timing-target and placement sweep, to establish how much of the current limit is movable without changing the design. I would not add a pipeline stage just to fix the 5.47 ns hop.

In order of priority for this netlist:

**First, take decode and architectural write-enable logic out of the operand path.** Trace why a decoded `rd` and `regfile.i_we` are on a path from the *consumer’s instruction* to its operand. The consumer should need little more than its source indices; the producers should already have registered destination indices and metadata saying whether they write a register and when their result is available. Distinguish a live forwarding producer from a W-stage register-file write strobe. Compute one set of mutually exclusive grants per operand—RF, X, M, or W—and compare that mapping with the current priority mux. In particular, check whether write-through and W forwarding implement the same choice twice. This is the best first RTL lever because it can remove both serial logic and long control nets without changing CPI. A **1–3 ns reduction on the affected path** is a useful experiment target, not a core-wide forecast. Expect a change on the order of tens of LUTs in either direction and modest test churn: priority, r0, load availability, and killed producers are the important cases.

**Second, improve locality and fanout.** Try a loose placement region for the decode, RF read, bypass, and operand-register logic, and inspect the endpoints of the slow nets before tightening it. If a grant really fans out across both operands or across a dispersed mux tree, try local copies of its driver and check that synthesis preserved them. Pure placement costs no LUTs or CPI and almost no functional test work; deliberate replication adds a little logic. Recovering **2–3 ns on the outlier hop** is plausible. Recovering that much on the *worst path of every seed* is a different proposition.

**Third, register bypass *control*, with a deliberate stage split.** If “register the forward-select result” means the selected operand data, `dx_a` and `dx_b` already do that. Another register after the mux does not shorten the instruction-to-mux path. The useful split is to register early source matching or grants, then perform the final data selection next cycle. Those grants must describe **where the producers will be when the data is selected**, including when a stage holds, advances, or is killed. Registering the old X/M/W select and applying it to next cycle’s buses is wrong. This can remove several nanoseconds from the specific D path if the cut separates the long control hops. Budget extra metadata flops, modest additional LUT logic, and substantially more hazard testing. The extra stage need not cost an ALU-dependency bubble if the live X bypass still feeds the final operand register. It can, however, increase redirect latency.

**Fourth, add a full stage if you need a larger frequency step.** A sensible cut is early decode/RF work on one side and final operand resolution on the other. This gives more freedom to balance the paths than registering a few grants, but an early RF value can go stale while the instruction waits: a producer can write back and disappear from the bypass window before the operand is consumed. Keep the read late or explicitly cover that case. Expect tens of extra FFs, some hold/kill and bypass logic, and the most pipeline-test churn of these options. Straight-line issue can still be one per cycle. A later branch-resolution point can cost another slot, and simply inserting a stage **after** operand selection can introduce an adjacent ALU dependency stall unless the bypass is moved with it. This is the higher-upside option, but it does not by itself shorten X-to-X forwarding.

**Last, split the three-way bypass data mux into registered halves.** I would do this only if the new reports actually point at the data mux. Your main path spends much of its time *getting to* that mux. A partial early selection also adds an operand-width register bank and complicates source age and load readiness, for no guaranteed LUT saving. If you do try it, leave the newest producer on the late side; otherwise you risk trading essentially every adjacent ALU dependence for a bubble.

## 2. Can placement alone fix the 5.47 ns net?

**It can fix that hop. It probably cannot fix the underlying path across seeds.** If the hop drops from 5.47 ns to 2.5 ns and nothing else changes, that particular 13.82 ns path becomes about 10.85 ns. That is a useful bound on the opportunity, not a prediction of 92 MHz: moving the endpoints also changes adjacent routes, and other paths are already near 14–16 ns.

Inspect the driver location, sink locations, fanout, and delay to the *specific critical sink*. One remote sink calls for a different fix from a write-enable that must reach several spatially separated cones. For the former, try a loose region or a different timing target with the heap placer. For the latter, localize or replicate the driver, or stop using that global write strobe as a forwarding predicate. Keep the nearby EBR and DSP endpoints in view; compacting the RF cluster can make the load and multiply return paths worse. Check that the intended target applies to the actual PLL-derived clock in FullTop.

The seed evidence says there are **both** effects: the 5.47 ns hop is placement-sensitive, but when it goes away, several medium hops still connect the same serial decisions. Judge changes on the FullTop worst and median results and on which path classes remain, not on whether one named net disappears.

## 3. Where to cut LUT4 first

**Try a replicated distributed-RAM register file first.** Make one 16×18 copy per independent read port and broadcast writes. That is replication *by read port*, not banking by register address. If Yosys maps it to native ECP5 distributed RAM, the storage itself is on the order of **36 RAM LUTs before packing granularity and write-control overhead**, rather than 270 data FFs plus two large read trees. A net saving of **roughly 100–300 LUT4s is plausible**, but measure it on a full build: the existing RF cone has not been isolated, and validity and bypass logic eat into the saving. It could also help fmax by shrinking the read network. Verify the inferred cells rather than assuming an asynchronous memory declaration gets the mapping.

The sticking point is **runtime reset**, not just power-up contents. Keep a resettable valid bit per writable register, return zero for invalid entries, and handle r0 explicitly. Preserve same-cycle W visibility with an explicit bypass if the primitive does not guarantee the required behavior. This should preserve CPI and the ISA; test reset after writes, first write after reset, both ports reading the written register, and interaction with higher-priority forwarding.

A **synchronous EBR RF** is a reasonable second experiment if minimum LUT count is paramount. In the straightforward implementation it takes **two EBRs**, each with a read port and a copy of the write, so that two reads and a write can occur together. It can eliminate most of the same RF mux fabric, but not the validity and collision bypass. Synchronous read does **not** intrinsically imply a bubble per instruction or per dependency: it changes when addresses must be ready and when bypass is applied. Whether it fits an existing boundary or needs another stage is the real cost. For this core, distributed RAM is the smaller contract change.

**Ordinary address banking is not an area fix by itself.** Two 8-entry banks plus a bank-select mux reconstruct a 16-entry selector if both ports must read either bank. Providing only one read per bank saves hardware by introducing same-bank conflicts and arbitration. Halving the architectural file really does remove **144 data FFs** and approximately half the raw read-tree work, but it breaks the frozen ISA. I would not do that for this brief.

**Treat the constant LUTs and dedicated mux counts as clues, not savings estimates.** A constant half of a PFUMX can be the cost of how a sparse function was decomposed. Deleting the constant without changing that decomposition is not an option. Group those LUTs by cone and look for repeated masks after wide selections, replicated sign-fill logic, and result choices that can be combined before widening. Try changes by cone; **tens of LUTs** is a more credible initial goal than reclaiming 265. Likewise, 630 dedicated mux cells are not 630 additional LUT4s. Improve the functions and ownership of the mux trees, not the cell count in isolation. The forwarding ablation shows that the bypass network matters, but −158 is the netlist delta of **removing the feature**, not the expected saving from implementing it better.

The four-slot squash is a **throughput** target, not my first area target. Removing a slot only saves LUTs if it eliminates actual state or control logic. Prediction is more likely to add area.

## 4. Does the four-slot squash deserve a redesign?

**Yes, if those loops represent the workload and fmax stays at 65–75 MHz.** At 70 MHz, CPI 1.6–1.8 is about **39–44 million retired instructions per second**. A CPI improvement from 1.8 to 1.4 would improve throughput by about 29%, equivalent to taking 70 MHz to 90 MHz at the old CPI. Separate taken-redirect penalties, load-use stalls, and fill/drain before making that comparison; the startup cost is material in a five-iteration test.

First, draw the cycle timeline from **branch resolution to the first correct-path instruction accepted by D**. Distinguish slots lost to the registered redirect, to launching the new EBR request, and to discarding the old response. Look for a cycle you can reclaim while keeping the compare out of the same-cycle PC enable path. In particular, separate *whether an in-flight fetch is valid* from *whether the PC should advance*. A pending redirect with clear priority over a hold, plus appropriately delayed fetch validity, is a better starting point than putting a fast but long combinational squash back on the PC enable. Also consider early redirects for direct unconditional jumps if their target calculation fits without reviving the old critical path.

For counted loops, I would try **backward-taken before a one-bit history table**, provided you can supply the target early enough. A direction prediction that waits for the X-stage target does not avoid the fetch wait. Predicting in D can recover only some slots; a small tagged target cache can let a warm loop redirect at fetch, but adds a timing-sensitive lookup and recovery logic. In an ideal five-iteration loop with four taken backedges followed by one not-taken exit, an early, correct-target backward-taken prediction changes four taken penalties into one exit misprediction. At four slots each that is **12 cycles saved**, before accounting for cold starts or late predictions. A direction-only one-bit predictor can also miss on the first taken iteration after the previous exit.

I would therefore **try to remove a fixed redirect slot first**, then add backward-taken or a small target cache only if loop throughput warrants it. Check wrong-path stores, register writes, and HALT explicitly; compare/target recovery must never let any of them commit.

## 5. Arithmetic and premises

- **LUT accounting:** \(1561+2\times63=1687\) is correct, and the truth-table classes also sum to 1687. But that does **not** reconcile the reported CoreTop total of 1813. In FullTop, \(1645+152=1797\), not 1897. The residuals are 126 and 100 respectively. Reconcile raw mapped LUTs, carry expansion, and packed resource usage from the same build before interpreting those residuals or the PLL-wrapper delta. A LUT4 site is also not a physical tile.
- **RF mux count:** A binary 16:1 tree has **15** 2:1 nodes, so \(2\times18\times15=540\), not 576. The latter counts the data leaves. With r0 constant, a straightforward tree has 36 bottom-level choices with a constant input; those can simplify, but they do not all vanish. Neither count translates directly into PFUMX plus L6MUX21 usage. And LUT-to-LUT connectivity alone shows multilevel logic, not that all those LUTs implement muxes.
- **Routing fraction:** “78–84% of every critical path” is false. From the rounded splits, CoreTop is about **84%, 80%, 57%, and 47%** routing; FullTop is about **83%, 76%, 85%, and 81%**. The recurring decode/bypass path is routing-dominated. Some of the paths exposed when it improves are not.
- **Ablations:** ABC remapping makes small ablations **non-additive**, not meaningless. Zeroing the branch operands changes what the mapper can share and how it decomposes the surrounding logic. The result is valid for that modified netlist; it does not price the branch unit. For area, compare functionally equivalent alternatives and inspect their mapped cones. For timing, compare common seed sets and the resulting path families. A seed sweep measures placement sensitivity; it does not isolate a mapping change.
- **DSP margin:** 140 and 185 MHz correspond to about **7.14 and 5.41 ns** in the isolated tests. Subtracting those numbers from a 20 ns reference does not establish in-core slack. The relevant path includes the DSP’s real input and output routing plus everything between the DSP and the consuming register. You were right not to pipeline it based on the isolated number alone; likewise, the isolated number is not evidence that the in-core multiply bypass can be ignored.

## 6. What you may not be seeing

**The biggest unresolved issue is whether the named paths are the cones you think they are.** A path reported as DSP → `o_target` adder → forwarded value, or data EBR → `o_target` carry chain → D operand, is worth tracing pin to pin. If the branch adder really takes only registered X operands and its target is not an architectural writeback value, those paths cannot literally be using it in the way the names suggest. A mapped net can inherit a misleading name, or synthesis can share arithmetic behind a mux. If the dependency is real, separate the redirect target from the architectural link/result and keep late DSP and load results out of unrelated arithmetic before bypass. Do not waive a path merely because the instruction classes look mutually exclusive at the RTL level.

**For 100 MHz, plan around a 10 ns budget on three path families, not just D.** Shorten the decode-to-grant path, bound the late X/M-to-operand recurrence, and decouple squash/hold logic from the fetch CE. The best reported builds still need about **3.4 ns** off their worst path, and the worst FullTop build needs about **5.6 ns**. My best shot without changing the ISA would be **distributed-RAM RF plus early producer metadata, a short late bypass mux, and a separate registered redirect/validity mechanism**. Then add a pre-operand stage if the D boundary still needs it. If a correctly traced DSP or EBR return remains the limiter, consider making *that result* available one stage later and interlocking dependent consumers, rather than adding a blanket stall to every execution of the instruction. That is a CPI trade to measure, not free retiming.

**Memory depth will add bank selection right where you least want it.** A deeper instruction store adds a bank-output mux between EBR and instruction consumption; a deeper data store can add one directly on the load-forwarding path. You also get high-address bank decode on the request side, including on the store-commit path after effective-address generation. Carry the bank ID alongside each outstanding read and advance it on the same acceptance/hold conditions as the EBR response. Using the current address’s bank ID to select the previous read’s word is an easy bug to miss with one EBR. Check read-before-write behavior across the bank boundary, and verify that redirects and holds neither commit nor replay stores. If a registered output mux is necessary, budget the extra fetch or load-use latency explicitly.

Finally, before treating FullTop as a hardware baseline, **verify the PLL feedback topology and reset release**. The three divider values alone do not establish 60 MHz. \(25\times24/10=60\) assumes the feedback arrangement makes 600 MHz the VCO frequency *before* the output divide; ordinary divided-`CLKOP` feedback does not use that formula. Check `FEEDBK_PATH`, `CLKFB` wiring, the generated-clock constraint, and synchronized release from `LOCK`, then confirm the clock on the board. Static timing can rank these changes, but it cannot validate that the board is running the clock you constrained.
