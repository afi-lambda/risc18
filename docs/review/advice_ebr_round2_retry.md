2. **I’d run a PLL phase sweep into a nearby fabric capture flop.** Keep the EBR launch clock fixed and shift a second, same-frequency PLL output that clocks only the capture side. You can run the test at 60 MHz: the point is to vary the launch-to-capture interval, not to run the whole design near failure. Alternate between preinitialized addresses with complementary data, establish the address and enables well before launch, and check the captured value later on a relaxed path. At each phase, count old-word and new-word captures over many trials, for both transition directions. Keep placement and routing fixed across phase settings. An early phase should reliably see the old word and a late phase the new one; without both controls, a passing test can just be sampling a bit that never changed.

   With the PLL’s one-eighth-VCO-period fine phase step, a 600 MHz VCO gives a **nominal step of about 0.21 ns**. That is sweep resolution, not absolute clock-to-out accuracy. The transition measures EBR clock-to-DO **plus** the data route, capture setup and differential clock insertion delay. Use a nearby capture flop, inspect the routed path, and run a nearby fabric-flop reference with the same clock pair to check for an unexpectedly large clock offset. The failure mode is to subtract the reported data-route delay and call the remainder EBR clock-to-out while ignoring clock skew and capture setup. Report the transition band, not a single exact threshold. 4. **For this core, I’d rank the options as follows.**

   **First, distributed RAM for the register file and small tables.** This is the option that actually removes the EBR clock-to-DO arc. Reads become address-to-LUT-to-output paths, with depth muxes and routing as applicable; they are not free, but you can place the read boundary where it helps. Budget roughly one storage LUT per bit per 16-deep bank per read copy, before native packing, write control and mux overhead. A 16×18 two-read, one-write file is therefore on the order of 36 storage LUTs before overhead, with writes broadcast to both copies. Deeper files add banks and muxes; extra independent write ports are not obtained by simple replication.

   **Second, issue the EBR read earlier when the address is already known.** This is my unlisted option for arrays that should stay in EBR. It moves the read stage rather than speeding it up. The cost is address, tag and valid state, possibly a small buffer, and sometimes a wasted read-port slot on a redirect. It helps predictable fetches or table lookups, not a data-dependent address that becomes known late.

   **Third, use 36-bit mode when the operands really are paired.** A 512×36 organization can fetch two 18-bit halves at one address with little selection logic if both halves are consumed. It trades depth and port flexibility for width: the wide pseudo-dual-port organization is not two independently addressed read ports. Check lane-write support and what the flow actually infers; otherwise a half-word update can cost a read-modify-write. This can remove a second access, not the first access’s clock-to-out.

   **Fourth, interleave two blocks for bandwidth.** It costs two blocks where one may have held the capacity, plus bank steering and usually a return mux. It gives concurrent accesses when they land in different banks, subject to each bank’s port configuration; conflicts still need handling. A single access is not faster by construction, and an unregistered bank mux can make the read stage worse. I’d rank it above wide mode only if the measured bottleneck is independent accesses that usually hit different banks.

   **Fifth, narrow the organization with byte or word selection.** Do it for capacity or access granularity, not on the assumption of a faster timing arc. Lane selection can add LUTs, and assembling an 18-bit operand from narrower accesses costs either parallel blocks or ports, or extra cycles. Unless a matched timing report shows a materially faster arc for the narrower mode, treat it as a width change, not a change to the read stage.
